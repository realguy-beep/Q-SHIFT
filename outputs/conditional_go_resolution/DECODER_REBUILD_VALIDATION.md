# Decoder rebuild validation

## Implementation checked

The installed versions are Stim **1.16.0** and PyMatching **2.4.0**. The fixture constructs a rotated Z-memory surface-code circuit at distance 3 and 5 rounds, obtains a decomposed Stim detector error model, and creates a PyMatching decoder from that DEM. A changed but valid parameter pair creates a second circuit/DEM/matcher. The same topology and detector definitions are used throughout.

The current PyMatching API exposes edge inspection and insertion (`edges`, `get_edge_data`, `add_edge`, boundary-edge methods), but no public `set_edge` method. Direct in-place weight mutation is therefore not used. The safe update pattern exercised here is: build a new matching instance, validate its schema, keep the active instance pinned for the current block, then replace the active reference under a lock after the block completes.

## Deterministic fixture results

Generated by [decoder_rebuild_fixture.py](decoder_rebuild_fixture.py), saved in [FIXTURE_RESULTS.json](FIXTURE_RESULTS.json):

- Noiseless distance-3/five-round circuit: **40 detectors, 1 observable**; 32 sampled shots had all-zero detector and observable data.
- Old and rebuilt DEMs both had **570 error terms and 142 matching edges**. All 142 common edge identities remained graph-consistent, and all 142 edge weights changed under the data-heavy/measurement-heavy parameter change.
- Both rebuilt and independently constructed reference matchers gave exactly identical predictions on all **2,048** paired detector samples. Prediction shape was `(2048,)`.
- The old and new matching predictions disagreed on **0/2,048** samples, and both had 4 residual logical errors on this small sample. This is not evidence that their weights are generally utility-equivalent; it shows that changed weights do not guarantee a changed decision on a finite sample.
- Candidate DEM-to-matcher rebuild latency: one run **2.45 ms**; across 25 repeated tiny rebuilds median **2.291 ms**, 95th percentile **2.401 ms**. This is local process timing for one d=3/five-round circuit only.
- Process working set was **79,413,248 bytes before** and **82,649,088 bytes after** constructing three persistent decoder versions plus temporary rebuild probes (increase **3,235,840 bytes**, about **3.09 MiB**). This includes Python, Stim and native PyMatching allocations, allocator behavior, and loaded libraries; it is not an isolated per-matcher allocation measurement.

The measurement-heavy fixture was sampled under the changed generating model; the decoder prediction comparison was paired. A decoder constructed from an independently regenerated identical DEM exactly matched the rebuilt instance. The changed model’s same-sample LER was 4/2,048, the same as the original model.

## Correctness tests

Command:

```powershell
python -m unittest -v test_decoder_rebuild_fixture.py
```

Result: **5 tests passed**. Coverage checks detector and observable counts, noiseless behavior, identical predictions from independent reference construction, enforced block order, rejection of a mid-block swap, and use of the new decoder only on the subsequent block.

## Scope limits

This validates PyMatching reconstruction and a single-process block-boundary replacement abstraction. It does not validate concurrent hardware streams, hard real-time deadlines, multi-observable graphs, correlated-edge metadata beyond the native decomposed DEM used here, or a physical controller integration. The measured 2.3 ms graph-build time cannot be compared with a hardware QEC cycle until a target platform, batch duration, and deadline are specified.
