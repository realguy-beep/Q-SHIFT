# Proposed finite-history estimator study

**Status: design proposal only. No sampling, seed generation, protected-data access, or study authorization.** This protocol compares detector-only parameter accuracy. It does not test decoders or logical error rates.

## 1. Hypothesis and primary metric

Primary question: under a measurement-probability change, does Candidate B reduce burst-probability estimation error relative to source-faithful Candidate A?

Primary metric: for each held-out root in each of two measurement-change strata, compute the mean absolute burst error over post-change update blocks using a trailing 1,000-shot detector window. Each estimate is formed before the next 100-shot block and is scored against the generating parameters for that next block. Define paired root difference `D = MAE_B − MAE_A`; negative favors B. Average first within root, then equally across step-up and step-down strata. The primary estimand is conditional on the fixed analytical template bank and the model family specified below.

Secondary metrics: Candidate B measurement MAE; burst and measurement MAE at window sizes 200, 5,000 and 10,000; nominal-stationary error; gate-mismatch error; edge hits; objective residual; and estimator runtime/memory. This study makes no decoder-performance claim.

## 2. Arms and model families

- **A:** `CandidateA`, five p_b knots `{0,.005,.010,.015,.020}`, p_m fixed at `.003`, piecewise-linear interpolation, population-limit pooled scales and `.00001` search.
- **B:** `CandidateB`, same 45 features, two-dimensional `[0,.020]×[0,.010]` domain, `.001` template nodes, bilinear interpolation, `.0001` fitting grid, standardized objective and frozen tie rule.
- Primary template family: exact categorical circuit expectations from the existing balanced circuit and five independent burst sites.
- Prespecified model-sensitivity arm: approximate DEM templates kept separate, with Stim conversion flags fixed to `decompose_errors=True, approximate_disjoint_errors=True`.
- Gate p is fixed in both estimators at `.003`. It is not estimated. Candidate C and D are excluded.

## 3. Prespecified conditions

Use `p_b=.008` throughout. Five conditions:

1. Stationary nominal: `p_m=.003`, gate p `.003`.
2. Measurement step-up: `p_m=.003` for shots 1–5,000, then `.006`; gate p `.003`.
3. Measurement step-down: `p_m=.006` for shots 1–5,000, then `.003`; gate p `.003`.
4. Gate-low stationary stress: actual gate p `.002`, `p_m=.003`.
5. Gate-high stationary stress: actual gate p `.004`, `p_m=.003`.

The gate stresses rescale only the existing balanced categorical P1/P2 rates. They do not add a noise mechanism. Actual parameters and condition labels are held for offline scoring and never passed to either estimator. No noise point may be changed after held-out results are inspected.

## 4. Histories, chronology and splits

Proposed allocation: 20 independent development roots per condition and 40 independent held-out development-evaluation roots per condition. Each root has 10,100 chronological shots so the final 10,000-shot estimate can be applied to and scored on a following 100-shot block. History lengths `{200,1,000,5,000,10,000}` are nested views of the same stream. This is 1,010,000 development shots and 2,020,000 held-out development-evaluation shots (3,030,000 total). All roots are newly created from explicitly authorized development-only seed namespaces after protocol approval; no Stage 5 or protected seed material is used.

At each 100-shot block boundary after the chosen warm-up, compute the estimate using only the most recent N detector rows strictly before the next block. The estimate first applies to the following 100 shots. No current-block detector can affect its own estimate. For the step strata, primary scoring begins after the change plus one full 1,000-shot history; both arms see identical detector rows. The estimator receives detector bits only; labels/true parameters are joined after estimates are written.

Development roots are used only for data-pipeline, storage and estimation diagnostics; there is no threshold or hyperparameter tuning. Held-out development roots remain unopened until estimator/configuration/template hashes and the scoring script are frozen. These are not protected or confirmatory evaluation roots.

## 5. Template calibration allocation

The primary proposed study uses deterministic population templates and scales generated by `generate_templates.py`; sampled template-calibration allocation is **zero shots** for both arms. A and B share the same exact/DEM model-family bank and the same analytical scale construction. This makes the primary inference conditional on correct model-generated templates and isolates finite-history estimation noise. Charge template-generation CPU once and separately by family.

This allocation does **not** measure uncertainty from empirically calibrated templates or real-device noise. If the scientific target includes calibration randomness, request a separately budgeted extension before data collection; do not silently mix sampled and deterministic template means.

## 6. Statistical analysis

The independent unit is the root/stream. Keep A/B paired within root. Report each stratum's root-level mean and SD, paired difference distribution, MAE for both parameters, edge-hit frequency, and missing/failed roots. Primary summary is the equal-weight average of the two step-stratum mean paired differences.

Proposed development interval: stratified Welch t interval on the independent root-level paired differences. For step stratum s, calculate mean `d_s` and sample variance `v_s` across roots. Primary estimate is `(d_up+d_down)/2`; estimated variance is `(v_up/n_up+v_down/n_down)/4`, with Welch-Satterthwaite degrees of freedom. Report a one-sided 95% upper endpoint for the signed difference and a two-sided 95% descriptive interval. Preserve raw root-level summaries and scenario-specific intervals. This is development uncertainty, not confirmatory evidence. Do not use shot-level independence intervals or bootstrap shots.

No practical margin is selected here. Interpret both absolute error units and normalized error; do not select a margin from results. Candidate B's measurement MAE is secondary and should be shown even if burst MAE is unfavorable.

## 7. Boundary, failures and stopping

Estimates are clipped by bounded search; any estimate at a parameter edge is flagged. Out-of-range or malformed detector inputs fail closed. A failed profile/template load aborts before histories are opened. Do not impute failed roots; report them and stop if failure is condition-dependent or breaks the paired comparison. No adaptive expansion of the grid or post-result feature selection.

Resource planning: uncompressed detector storage is approximately `3,030,000×40 = 121,200,000` bytes (about 121.2 MB), before metadata and copies; packed bits would be about 15.2 MB. Chunk roots and retain compact 100-shot estimate records. Template-bank size/hash is recorded at preflight. Peak RSS cap proposal: 2 GiB; abort if exceeded. CPU time is not benchmarked for sampled stream generation here; require an owner-approved runtime cap after a separately authorized resource preflight. No effect-based interim stop; stop only for integrity, resource, chronology, or data-quality failure.

## 8. Protected-test and authorization rules

No protected evaluation seeds, Stage 5 outcomes, or final-test data may be read, enumerated, uploaded or used for tuning. The proposed held-out roots are newly generated development roots only. Any later confirmatory evaluation needs an independently frozen protocol and separate explicit authorization. This proposal itself is not an authorization to sample.

## 10. Phase 3B execution-integrity addendum

This addendum specifies runner mechanics and does not change either estimator, the primary estimand, the five condition schedules, root allocation, nested history lengths, model-family arms, or statistical analysis above.

- The executable verifies exact hashes for this protocol, the study configuration, template bank, runner, estimator, analyzer, template generator, and circuit-builder source, plus a fingerprint of the Python/NumPy/Stim versions. Approval also binds the seed-manifest SHA-256 and stable manifest ID, development-only scope, exact condition and split allocation, approved maximum roots/shots, an explicit CPU limit, a memory limit no greater than 2 GiB, expiry, approver, and approval reference.
- Sampling is replayed causally in blocks. At boundary `t`, each eligible estimate uses only `detectors[t-N:t]`; all A/B and exact/DEM fits share that computed feature mean. The estimate is recorded for the next block before that block is requested from the sampler. At the 5,000-shot transition, the first new-condition block is sampled only after the boundary estimate. The primary step-change analysis remains restricted to `t >= 5,000 + N`.
- Each root is the checkpoint unit. Root files contain a checksum over canonical JSON, a hash of the exact seed-manifest root entry, and the approved run fingerprint. The checkpoint index and final result are written through same-directory temporary files followed by atomic replacement. Resume verifies every hash, adopts complete orphan root files, skips verified completed roots, and refuses corrupted or mismatched artifacts. Partial temporary files are preserved in an `incomplete_checkpoints/` directory and the corresponding unfinished root can be recomputed from the same pre-approved seeds.
- Root order is lexicographic by `(split, scenario, root_id)`. Within a root, records are ordered by chronological boundary, then history length, template family in configured order, and arm `A` before `B`. Final JSON is streamed from root checkpoints so the runner does not accumulate the full study in memory.
- On Windows, checkpoint temp and destination files are kept on the same volume and replaced with `os.replace`; file contents are flushed with `fsync`. Python does not provide a portable directory-entry `fsync` guarantee on this platform, so sudden power-loss durability of rename metadata is not claimed. Checksums detect incomplete or corrupted artifacts on restart.

The approval schema is `qshift-finite-history-approval-v2`. This package contains no such approved record and no production seed manifest. The records created by unit tests are ephemeral fixtures in temporary directories, marked test-only, and are used only with mocked deterministic detector blocks.

`finite_history_pilot_config.json` proposes a separate, development-only execution check with two roots per condition (10 total) and no held-out-development allocation. It retains the same five condition schedules and 10,100 shots per root but is not the primary estimator-comparison analysis and must not be pooled into the 3.03-million-shot proposal. It has no seed inventory or authorization; any execution requires a new approval binding its own config and seed-manifest hashes.
